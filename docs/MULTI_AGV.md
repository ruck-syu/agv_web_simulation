# Two-AGV backend (Phase 1)

## Start and navigation choice

`docker compose up -d --build` now launches `agv_fleet.launch.py`: one authoritative two-robot physics process, one fleet coordinator and one rosbridge at ws://localhost:9090. Native equivalent: `ros2 launch agv_web_bridge agv_fleet.launch.py`. Spawns in world metres are agv1=(-2.8,1.6,0), agv2=(4.5,1.6,0). Both spawns are collision-validated at startup. Never launch the old simulator alongside this launch.

Fleet mode uses independent geometry planners and differential-drive controllers. Four-connected 0.25 m A* supplies a baseline; farthest-visible string pulling removes grid staircases. Continuous segment checks enumerate every crossed cell interval against the circumradius-inflated map (including the half-cell diagonal margin), world bounds, and peer clearance. Tangent circular fillets use a 0.65 m radius with <=0.06 m arc samples, then <=0.08 m trajectory samples. Unsafe fillets retain their collision-free corner and may require a pivot. This is near-optimal shortcutting, not a proof of globally shortest curvature-constrained routing; no path is allowed to cut a rack footprint.

The fleet launch's `autonomous_cruise_speed` argument sets the coordinator's startup ROS parameter of the same name. It defaults to **1.0 m/s** and accepts a finite value in `(0, 1.2]`. Invalid values produce a fatal startup diagnostic and a nonzero exit. For example, run `ros2 launch agv_web_bridge agv_fleet.launch.py autonomous_cruise_speed:=0.9`.

The regulated pure-pursuit controller estimates curvature from adjacent trajectory samples and looks ahead for lower speed limits. For distance `d` and target speed `u`, the braking cap is zero when `d ≤ τu`. Otherwise it takes the larger of `u` and `sqrt(u² + 2a(d − 0.04u) + (aτ)²) − aτ`. The corner reserve `0.04u` covers one truth sample period. The model uses `a = 1.2 m/s²` and nominal `τ = 0.14 s` (100 ms control plus 40 ms truth). The speed cap on curvature κ is the smaller of `1.2/|κ|` m/s and `sqrt(0.3/|κ|)` m/s. A 0.65 m radius fillet therefore slows to about 0.44 m/s. The endpoint has a zero speed limit and a proportional final approach. Arrival requires position within 0.020 m, yaw within 0.08 rad, linear speed at most 0.03 m/s and angular speed at most 0.15 rad/s.

Pursuit lookahead increases with speed, from 0.25 to 0.55 m at the default cruise. The controller shrinks the lookahead through dense samples when clearance is tight. Each candidate must pass the chord check, a short current-heading travel check, and one second of constant-twist and acceleration-limited arc checks. The controller tries a slower command along the same curvature if the full-speed sweep is blocked. It brakes before pivoting or replacing a moving route.

Localization is explicitly simulator ground truth in the shared `world` frame. This is a sound simulation-only choice: ground truth is the authoritative localization source, wheel odometry remains independently measured and published, and fresh truth is required for motion. Dynamic TF `world -> agvN/odom` corrects wheel error; `agvN/odom -> agvN/base_link` remains encoder-derived. There is no fleet SLAM map, map topic or NavigateToPose action server. This is not a substitute for localization on physical robots and does not test Nav2/SLAM behavior.

The original single-robot `agv_navigation.launch.py`, `agv_mapping.launch.py`, navigation bridge, map_cache.py and maps/ checkpoint remain available unchanged. Use that launch explicitly for the existing SLAM/Nav2 workflow. The Phase 1 fleet launch does not load, alter or invalidate saved SLAM checkpoints. Existing documentation describing SLAM and unknown-space rejection applies to that legacy launch; fleet mode deliberately plans in the simulator geometry map instead.

## Collision and sensor model

Both SimulationNode instances run in the same single-threaded ROS executor. Each proposed physics step checks the other robot's current padded oriented rectangle, so both cannot independently accept overlapping moves. The fleet simulator accepts only fresh stamped coordinator velocity commands, keeps the newest queued command, and clears motion targets after 0.25 s without a fresh command. The watchdog and 50 Hz physics use steady time. Acceleration and wheel limits, geometric rack blocking and encoder integration also apply. Both LiDAR planes include the other robot as a rectangular obstacle. For roof-scan visibility the peer collision box includes a simulated reflector reaching 1.2 m (body is 0.96 m, roof scanner 1.02 m). This is a geometric sensor model, not mesh tracing.

## Coordination protocol and limits

Every autonomous goal enters the coordinator. Parked and moving peers remain 3.3 m centre-clearance obstacles. Instead of locking the entire route, each tick atomically replaces that robot's held tiles with only its next 2.0 m of centreline, starting at current truth. Tiles are 0.5 m squares expanded by 1.3 m. Behind-route tiles disappear on renewal; failed renewal stops motion and contracts the hold to the current footprint. A waiting request can own no tiles, but its body remains a planning obstacle. Manual reservation gating sees these same short holds.

Current-peer conflicts are checked every 100 ms against the horizon. At 1.0 m/s the one-body stopping distance is 0.557 m with normal 0.14 s latency. At the 1.2 m/s ceiling with the 0.59 s stalled-coordinator budget below, one body travels at most 1.308 m before stopping, within the 2.0 m held centreline and the 2.0 m predicted-peer horizon. Each robot holds its own braking distance. Safety/conflict replanning bypasses optimizer timing; waiting retries occur every 1 s. Every 2 s, a full remaining-route search also replaces a detour if peer motion makes a route at least 0.75 m shorter. This avoids committing to an obsolete rack-end detour while suppressing small steering changes. Route search accounts for current peer poses; lower-priority search also considers samples along the winner's predicted next 2 m, and tries an alternate route excluding held tiles. Arrival timestamp then robot id provides deterministic priority without globally blocking unrelated younger requests. If a lower-priority body blocks the winner, the coordinator performs BFS over reachable free cells for holding points at least 3.8 m from the winner's full remaining route and destination. Candidates must belong to the component reachable from the original goal with the winner parked at its destination. That search runs on demand and is reused while both goals stay fixed. During travel the ROS coordinator searches from pose and reservation snapshots on a worker. The control tick checks current poses, separation and rolling reservations before adopting a result. Escape routes must acquire their rolling reservation against current peer occupancy. This prevents choosing the far end of a corridor that the winner will later block. For separately dispatched goals within 3.3 m of each other, the lower-priority robot can still yield to a clear bay so the winner can finish. A blocked second destination reports the parked peer explicitly. The search is discrete and does not prove complete multi-agent delivery. A disconnected bay cannot be reached; a bay requires a traversable entrance.


The 8 s no-progress watchdog releases and replans, with a fresh progress window; a 30 s waiting deadline extends only while an identified holder translates (rotation alone does not refresh this deadline), and the absolute 180 s request deadline remains. Thus unsatisfiable geometry terminates rather than waiting indefinitely. A destination within 3.3 m of a parked peer fails explicitly. A route severed by a parked peer also fails promptly when removing that peer restores reachability. Priority plus holding-bay yielding resolves the tested narrow-aisle case; this is not a completeness proof for arbitrary multi-agent planning. A robot parked at the only aisle entrance can make the other destination physically unreachable.
Ground truth older than 0.12 seconds suppresses motion commands while requests remain active. The existing 1.5-second freshness timeout still cancels autonomy and sets fleet safety stop. Centre separation below 3.0 m triggers a stop (clears at 3.3 m); constrained manual retreat remains available with fresh telemetry; active goals are canceled into safety_stop. No automatic movement resumes from a separation stop. Each robot additionally needs fresh odom and floor scan (<1.5 s); autonomy requires its own `alive` heartbeat (<2 s). Lost heartbeat cancels the goal. Manual takeover cancels the robot's route and old commands; manual motion is also gated against another robot's reserved corridor using a one-second projected sweep. The coordinator publishes the fleet actuator stream. Use the operator command topics for manual or autonomous requests. These are simulated operational safeguards, not safety-certified hardware controls.

## Frontend ROS contract

The frontend operates both namespaces independently. Static rack previews now run the same grid A*, string pulling, 0.65 m fillets and trajectory sampling as the backend. `frontend/src/navigation/fleetGrid.json` is a compact run-length export of the authoritative static collision map. Regenerate it after geometry/inflation changes using `scripts/export_fleet_grid.py` in the built ROS image, use its `--fixtures` option to refresh `frontend/tests/fixtures/fleetRoutes.json`, then run the point-for-point frontend/backend fixture test. Dynamic peer detours and yields are displayed from `/agvN/plan`; static previews cannot predict future operator goals. The existing 3D and overhead polyline renderers consume the dense trajectory directly without splines that could cut corners.
All JSON below is carried in `std_msgs/msg/String` as `{ "data": JSON.stringify(payload) }`. Fields in actual ROS messages retain their standard shapes. All fleet goal/plan/truth coordinates are `world` metres, yaw radians counter-clockwise, never the saved SLAM `map` frame. The Three.js conversion remains (x,z)=(world.x,-world.y).

Replace `N` with 1 or 2:

Fleet snapshot example (tile lists shortened):

```json
{
  "schema_version": 1,
  "frame_id": "world",
  "stamp": 1794937000.0,
  "safety_stop": false,
  "separation_m": 7.3,
  "robots": {
    "agv1": {"state":"navigating","detail":"Following reserved world route","mode":"autonomous","goal":[-0.8,1.6,0],"pose":[-2.8,1.6,0],"waiting_on":[],"ready":true,"busy":true},
    "agv2": {"state":"waiting","detail":"Planning and requesting route zones","mode":"autonomous","goal":[-3,1.6,0],"pose":[4.5,1.6,0],"waiting_on":["agv1"],"ready":true,"busy":true}
  },
  "reserved_zones": {"agv1":[[-6,3],[-5,3]],"agv2":[]}
}
```

Tile `[i,j]` covers world rectangle `[i*0.5,(i+1)*0.5] x [j*0.5,(j+1)*0.5]`. waiting_on lists blocking/earlier queued robot ids, or `occupied_or_unreachable` when no path exists. pose/goal can be null before telemetry or after completion; separation_m is null if either truth stream is stale. States: idle, manual, waiting, navigating, succeeded, canceled, unavailable, failed, safety_stop. `ready` requires that robot's fresh truth/odom/floor scan and heartbeat; fleet `safety_stop` independently cancels autonomous movement and permits only constrained manual retreat with fresh telemetry. A waiting request remains busy; terminal failure/safety_stop clears goal and requires operator resubmission. Status is a new fleet contract: legacy Nav2 lifecycle readiness fields are absent.

Start both checks readiness, measured speed and reachability before either request starts. New individual and paired goals require at least 3.32 m of live centre separation. Start both is disabled in the dashboard below that distance. It rejects any source/source, destination/destination or mixed pair of stops closer than 3.32 m (3.3 m parked-peer clearance plus 0.02 m arrival tolerance). Each robot advances to its destination as soon as it arrives at its own source. A failure, timeout, cancel, or superseding goal aborts any active peer leg; a completed route stays complete. Legacy pair commands can omit `destinations` for one goal per robot. The global Stop all shares the Start both publisher and topic so it follows pending pair admission in publication order.

The separation latch triggers below 3.0 m centre distance and clears at 3.3 m. The common linear cap ramps from 1.2 m/s at about 6.84 m to 0.45 m/s at 5.10 m and holds 0.45 m/s inside that point. For a two-robot approach from outside the braking band, both robots can spend up to 0.34 s at the 1.2 m/s ceiling before braking (0.12 s truth age, 0.10 s control period, 0.10 s command age and 0.02 s physics step). With 1.2 m/s² braking, they settle to at most 0.45 m/s by 3.253 m even at maximum closure. Pair admission also checks the measured speeds against the cap inside the band.

For a coordinator-controlled approach at or below that cap, normal braking allows a further `2 × (0.45 × 0.34 + 0.45²/(2 × 1.2))` m of closure from the threshold. The resulting minimum is **2.525 m**. Adding the full 0.25 s robot watchdog gives a stalled-coordinator minimum of **2.300 m**. If communication instead fails while the robots are still braking down from cruise, using 1.2 m/s at 5.10 m and the full 0.59 s budget gives **2.484 m**. The lower stalled bound of 2.300 m leaves **0.422 m** over the 1.878 m arbitrary-yaw contact distance. The bounds assume the default simulator's rates, speed and braking limits, the stamped command-age check, and an approach that enters the braking band under coordinator control or starts inside it at a separation of at least 3.0 m and at or below the near-peer cap.

Autonomous goals must be resubmitted after a separation stop. With fresh truth and sensors, manual retreat remains available at up to 0.2 m/s and 0.3 rad/s. The sampled retreat arc must maintain or increase centre distance to the peer.

Manual reservation gating checks a one-second constant-twist arc. It rejects increasing overlap with held tiles or approaching them within the reservation clearance, while allowing escape from an existing overlap. A zero/expired manual command still stops normally.

`/fleet/state` remains schema version 1 with the same fields and types. `safety_stop=true` now permits the constrained manual retreat described above; it still cancels autonomous navigation. `detail` supplies the explicit parked-peer failure reason. `waiting_on` may also identify an earlier queued request that owns no tiles yet. The optional `request_id` string on goal commands is echoed in robot navigation status and fleet robot entries, including terminal states after `goal` clears. Omitted ids are returned as null; existing fields and schema version 1 remain compatible. This lets the UI distinguish immediate completion from queued stale terminal status. No state names were added.

## Rolling-reservation additions (2026-11-18)

Schema version 1 and all existing state names, fields, request_id correlation, heartbeats and manual-retreat rules remain. Optional per-robot additions: `replans` (integer count of accepted plans), `yielding` (boolean temporary holding-point route), `reservation_lookahead_m` (number, 2.0). `detail` distinguishes following, holding and yielding; `reserved_zones` now describes the rolling horizon, not the entire trip. The published path is the actual smoothed trajectory followed, including temporary yield paths.

Acceptance evidence and per-robot sampled timelines are in `test_logs/fleet_concurrency_smoke.json`; the runnable harness is `scripts/fleet_concurrency_smoke.py`. It commands the live compose domain 72, unlike isolated-domain unit tests. An interrupted earlier run is preserved separately and must not be counted as a success. Static length comparisons exclude dynamic detours; travelled length includes yielding, braking and tracking. Heading rates are estimated from sampled ground-truth yaw; rotation episodes count commanded zero-linear/nonzero-angular intervals.

Current review validation and remaining fuzz limitations are recorded in FLEET_ROLLING_VALIDATION.md. Re-export/grid drift is checked by the ROS unittest suite through `scripts/export_fleet_grid.py --check`; fixture comparisons exercise `planFleetRoute`, and the unused visibility-graph planner was removed. Frontend and backend reject continuous endpoints beyond ±31/±19 m, including points that round to an in-bounds grid cell. Invalid/unavailable requests echo their new request_id. The grid and documentation do not depend on ignored test logs for correctness.
